3. Conflit provoqué sur une ligne du README

Deux branches modifient la même phrase de la section Sécurité. La première est fusionnée sans problème ; la seconde entre en conflit :

$ git merge --no-ff -m "merge: doc taille du jeton" feature/readme-tests
Auto-merging README.md
CONFLICT (content): Merge conflict in README.md
Automatic merge failed; fix conflicts and then commit the result.

- `session_regenerate_id(true)` après connexion ; cookie `HttpOnly`, `SameSite=Lax`.
<<<<<<< HEAD
- Jeton CSRF aléatoire de 32 octets, comparé avec `hash_equals()` sur toute écriture,
  y compris les `DELETE`.
=======
- Jeton CSRF aléatoire de 32 octets (256 bits), comparé avec `hash_equals()` sur toute
  écriture.
>>>>>>> feature/readme-tests

Résolution : on garde les deux apports, pas l'un contre l'autre. Les marqueurs sont supprimés, puis la fusion est validée :

- Jeton CSRF aléatoire de 32 octets (256 bits),
  comparé avec `hash_equals()` sur toute
  écriture, y compris les `DELETE`.
$ git add README.md
$ git commit --no-edit
[main cef035e] merge: doc taille du jeton

$ git log --oneline -1
cef035e merge: doc taille du jeton

Vérification après la fusion : les scripts de test alors en place sont relancés et passent (0 échec), et aucun marqueur ne subsiste dans le fichier.

6. Ce que l'équipe retient

  • Branches courtes. Une branche qui vit plus d'une séance accumule les conflits ; ici chaque branche porte un commit et meurt le jour même.
  • Le conflit se résout en lisant les deux versions. Fusionner en gardant un seul côté aurait perdu une information documentaire correcte.
  • Une fusion se teste. Le conflit portait sur de la documentation et n'a rien cassé — vérifié plutôt que supposé.
  • Le graphe sert de preuve. --no-ff rend chaque revue visible : c'est ce que le jury peut contrôler.
